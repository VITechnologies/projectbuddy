Run the workload, oracle and MCP tests: `.venv/bin/python -m pytest -v -p no:cacheprovider "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_seeded_ui_states_and_event_ids_are_repeatable" "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_independent_oracle_scores_seeded_task" "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_wrong_action_is_recorded_without_leaking_success_or_expected_target" "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_oracle_detects_a_faulty_workload_scenario_generator" "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_oracle_scores_model_state_claim_separately_from_task_success" "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_invalid_or_duplicate_action_does_not_allow_a_retry" "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_scenario_seed_is_strictly_bounded" "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_http_ui_exposes_public_state_and_has_no_action_write_route" "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_stdio_mcp_server_exposes_only_exact_ui_action_and_returns_no_oracle_data" "scripts/tests/test_assisted_benchmark_synthetic_ui.py::test_mcp_handlers_reject_wrong_task_malformed_action_and_duplicate_submission" "scripts/tests/test_assisted_benchmark_live_policy.py::test_stdio_ui_action_flows_through_server_set_broker_router_and_oracle"`. ## Required observation

1. Step 4 exits with code 0 and reports `16 passed`, with a `PASSED` line for each selected test, including `test_independent_oracle_scores_seeded_task[99-approve]`, `[100-hold]`, `[101-approve]` and `test_scenario_seed_is_strictly_bounded[-1]`, `[4294967296]`, `[True]`, `[1.0]`.
2. Same seed, same sequence (REQ-123 criterion 1, "For a fixed workload version and seed, the UI produces the same finite state sequence, visible controls, and ordered event ... identities"; SYS-REQ-031 criterion 1, "A fixed workload version and scenario seed produce the same finite UI-state and evidence-event sequence"): `test_seeded_ui_states_and_event_ids_are_repeatable` shows two seed-101 workloads with different clocks give equal `visible_view()` (workload version, task ID, state, controls `approve` and `hold`, event ID) and equal acknowledgements of `approve`; `test_independent_oracle_scores_seeded_task` shows the acknowledgement is exactly `{"accepted": True, "taskId": <task ID>, "state": "decision_recorded", "eventId": "<task ID>-event-0001"}`; seeds -1, 2**32, `True` and `1.0` raise `SyntheticUiError` matching `seed is outside`.
3. Finite transitions (REQ-123 criterion 1, "finite state sequence"): in `test_invalid_or_duplicate_action_does_not_allow_a_retry`, target `oracle_result` raises `SyntheticUiError` matching `target is not available` and leaves `visible_view()` unchanged, and a second action after `approve` raises `SyntheticUiError` matching `exactly one action`.
4. What the agent side receives (REQ-123 criterion 2, "approved action results", and criterion 3, "never through ... MCP tools/results"; SYS-REQ-031 criterion 2, "approved tool responses" and "absent from ... MCP results"): the stdio MCP server reports name `projectbuddy-synthetic-ui`, version `1.0.0`, and exactly one tool, `click_target`, whose input schema is exactly `taskId` (string) and `targetId` (string, enum `approve`, `hold`), both required, with `additionalProperties` false; a call with an extra argument is an error; the call `{"taskId": "synthetic-00000064", "targetId": "hold"}` returns exactly `{"accepted": True, "taskId": "synthetic-00000064", "state": "decision_recorded", "eventId": "synthetic-00000064-event-0001"}`, which contains neither `oracle` nor `expected` in any case; a following `approve` call is an error; the UI view reads `awaiting_decision` before the calls and `decision_recorded` after. The acknowledgements in `test_independent_oracle_scores_seeded_task` contain neither `oracle` nor `expected`, and the wrong-action acknowledgement contains neither `correct` nor `success`, in any case.
5. Agent-visible errors (REQ-123 criterion 3, "never through ... agent-visible errors"; SYS-REQ-031 criterion 2, "absent from ... agent-visible errors"): in `test_mcp_handlers_reject_wrong_task_malformed_action_and_duplicate_submission`, an unknown tool, a list-valued `targetId`, another task ID and an extra argument each return `is_error` true with no `oracle` text in any case, and the workload stays `awaiting_decision`; the valid call then succeeds and its repeat is an error.
6. Public UI surface (REQ-123 criterion 2, "The agent sees only the ... UI", and criterion 3): in `test_http_ui_exposes_public_state_and_has_no_action_write_route`, `GET /api/view` contains `"reading":` and `"limit":` but neither `expectedTarget` nor `oracle` in any case, and `POST /api/action` fails with HTTP 405.
7. The oracle decides the outcome (REQ-123 criterion 4, "A task passes only when the oracle observes the expected terminal state after the authorized UI action; model text alone cannot pass it"; SYS-REQ-031 criterion 4, "oracle-confirmed task completion"): before any action, `SyntheticUiOracle.evaluate` raises `ValueError` matching `no submitted action`; after the expected target for seeds 99, 100 and 101 it reports `state_grounded`, `action_correct` and `task_success` true; after the wrong target `approve` for seed 100 it reports `action_correct` and `task_success` false although the UI accepted the action. In `test_stdio_ui_action_flows_through_server_set_broker_router_and_oracle`, the fixed target `hold` is admitted by `LiveRunBroker` as the grant's `decision` choice and dispatched by `PinnedMcpRouter` to the stdio server; the view moves from `awaiting_decision` to `decision_recorded`, `evaluate_observation` on that view reports all three outcomes true, and `teardown_target()` names VM `00000000-0000-4000-8000-000000000002`.
8. Separate outcomes (REQ-123 criterion 5, "The oracle separately reports current-state/action correctness and terminal task completion"; SYS-REQ-031 criterion 4, "scores state grounding, action correctness, and oracle-confirmed task completion as separate outcomes"): a wrong state claim (`reading` 0, `limit` 0, seed 99) gives `state_grounded` false with `action_correct` and `task_success` true; a fault-injected scenario generator (reading 1, limit 0) with the matching claim gives `state_grounded` false with `action_correct` and `task_success` true, so the oracle does not take its expectation from the workload.
